# 08. 源码阅读与动手实验

## 1. 推荐源码阅读顺序

不要从几百行的配置类逐行硬啃。按“最小闭环 → 完整链路”的顺序更快。

### 第一轮：一次模型调用

1. `service/llm/LlmService.java`
2. `service/llm/impls/StreamLlmService.java`
3. `service/aimodelconfig/AiModelRegistry.java`
4. `service/aimodelconfig/DynamicModelFactory.java`

目标：说清活动模型配置怎样变成 `ChatModel` 和 `ChatClient`。

### 第二轮：一个完整节点

1. `workflow/node/IntentRecognitionNode.java`
2. `resources/prompts/intent-recognition.txt`
3. `dto/prompt/IntentRecognitionOutputDTO.java`
4. `workflow/dispatcher/IntentRecognitionDispatcher.java`
5. `IntentRecognitionNodeTest.java`

目标：说清输入、Prompt、结构化输出、state 和路由。

### 第三轮：RAG

1. `util/DocumentConverterUtil.java`
2. `service/vectorstore/AgentVectorStoreServiceImpl.java`
3. `workflow/node/EvidenceRecallNode.java`
4. `workflow/node/SchemaRecallNode.java`
5. `service/schema/SchemaServiceImpl.java`

目标：分清索引和检索，分清 `agentId` 与 `datasourceId` 过滤。

### 第四轮：Graph

1. `config/DataAgentConfiguration.java` 中 `nl2sqlGraph`
2. `constant/Constant.java` 中 state key
3. `workflow/dispatcher/`
4. `service/graph/GraphServiceImpl.java`
5. `util/FluxUtil.java`

目标：能在纸上画出主路径和三条重试环。

### 第五轮：业务执行

1. `PlannerNode` / `PlanExecutorNode`
2. `SqlGenerateNode` / `SemanticConsistencyNode` / `SqlExecuteNode`
3. `PythonGenerateNode` / `PythonExecuteNode` / `PythonAnalyzeNode`
4. `ReportGeneratorNode`

目标：知道哪些输出是模型推测，哪些是数据库/Python 的真实结果。

## 2. 实验 0：只观察一次请求

准备一个已能正常运行的智能体，从前端提一个只需要单表聚合的问题。记录：

| 项目 | 记录内容 |
| --- | --- |
| 原始问题 | 用户实际输入 |
| canonical query | QueryEnhance 的结果 |
| Evidence | 命中了哪些知识 |
| Schema | 召回哪些表 |
| Plan | 几个步骤，各用什么工具 |
| SQL | 最终执行的 SQL |
| 真实结果 | 数据库返回什么 |
| 报告 | 哪些结论可由真实结果验证 |

这是后续所有实验的基线。

## 3. 实验 1：修改展示文本

难度：低；不改变 AI 逻辑。

在一个节点中修改“开始处理/处理完成”的展示文案，运行对应单元测试并从前端观察时间线。

学习点：区分 SSE 展示文本与 Graph state 业务数据。

## 4. 实验 2：为意图识别增加测试样例

难度：低；不调用真实模型。

在 `IntentRecognitionNodeTest` 中增加：

- 模糊追问，例如“那华东呢？”并提供多轮上下文；
- Prompt Injection 文本；
- DTO 缺失字段或错误分类值；
- 模型返回 Markdown 代码块的情况。

学习点：Prompt、结构化输出和业务校验的边界。

运行单测示例：

```powershell
.\mvnw.cmd -pl data-agent-management -Dtest=IntentRecognitionNodeTest test
```

## 5. 实验 3：打印最小化的模型诊断信息

难度：低到中。

为开发环境增加安全日志，只记录：

- 使用的模型名；
- 节点名；
- 调用耗时；
- 响应是否成功；
- token usage（供应商支持时）。

不要记录 API Key；对用户问题、Evidence、SQL 结果中的敏感内容做脱敏或仅记录长度/摘要。

学习点：AI 调用是外部依赖，需要可观测性。

## 6. 实验 4：观察召回参数

难度：中。

选择 10 个固定问题，先保存每个问题的期望表；然后分别调整 table topK 或 threshold，每次重新跑这组问题，记录：

- 正确表是否召回；
- 无关表数量；
- Prompt 长度变化；
- 最终 SQL 成功率。

不要只根据单个问题调参。学习点是建立最小离线评估集。

## 7. 实验 5：增加一个纯 Java Graph 节点

难度：中。

建议增加一个无模型、无数据库副作用的“问题长度/字符规范检查”节点：

1. 实现 `NodeAction`。
2. 从 `INPUT_KEY` 读取问题。
3. 输出一个新的 state key。
4. 在 `DataAgentConfiguration` 注册节点和边。
5. 为正常输入和空输入写单元测试。

学习点：Graph 节点、状态契约和边。先不要从增加一个 LLM 节点开始，否则问题来源太多。

## 8. 实验 6：增加一个结构化 LLM 节点

难度：中到高。

在实验 5 熟练后，可设计“查询风险分类”DTO，例如：

```text
riskLevel: LOW | MEDIUM | HIGH
reason: string
```

要求：

- 提示词独立放在 `resources/prompts`。
- 使用结构化校验 Advisor。
- 使用 `BeanOutputConverter`。
- Java 端再次验证枚举值。
- mock LLM 编写成功、非法 JSON、非法枚举和异常测试。

学习点：完整的结构化 AI 工程闭环。

## 9. 实验 7：增加一个只读 Tool

难度：高。

在 `McpServerService` 或独立服务中增加无副作用查询工具，例如“按 ID 获取智能体公开摘要”。确保：

- `@Tool` 描述清楚何时调用。
- 参数有明确描述和校验。
- 服务层执行鉴权/范围限制。
- 返回值简洁且不含密钥。
- 有单元测试。

学习点：Tool 定义、JSON Schema、应用执行和权限边界。

## 10. 实验后的复盘模板

每次修改后回答：

1. 改的是 Spring AI 层、Graph 层还是 DataAgent 业务层？
2. 新增了什么输入、输出或 state key？
3. 哪些行为是确定性的，哪些依赖模型？
4. 失败怎样传播，是否有重试上限？
5. 用什么测试证明没有破坏旧路径？
6. 是否引入数据泄露、越权、Prompt Injection 或代码执行风险？

## 11. 建议的两周学习节奏

| 时间 | 内容 | 成果 |
| --- | --- | --- |
| 第 1～2 天 | 01～03 + Intent 节点 | 能读懂 ChatClient、Flux、DTO。 |
| 第 3～4 天 | 04 + Evidence/Schema 节点 | 能解释 RAG 索引和检索。 |
| 第 5～6 天 | 06 + Graph 配置 | 能画出节点和重试路径。 |
| 第 7 天 | 07 完整追踪 | 完成一次请求跟踪笔记。 |
| 第 8～10 天 | 实验 1～4 | 会写 mock 测试并评估召回。 |
| 第 11～14 天 | 实验 5 或 6 | 独立增加一个受测试保护的节点。 |

学习目标不是“两周看完所有类”，而是掌握一种能持续读懂和修改 AI 工程的方法。
