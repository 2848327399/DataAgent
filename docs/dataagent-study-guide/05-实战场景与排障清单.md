# 05. 实战场景与排障清单

## 1. 已完成的产品数据场景

业务库：`product_db`

核心表：`products`、`orders`、`order_items`、`users`、`categories`、`product_categories`

已验证的典型问题：

```text
按订单状态统计订单数量
销量最高的商品是什么
统计每个用户的订单总金额
查询库存低于 50 的商品
```

这组问题练习了筛选、聚合、排序、`JOIN` 与库存条件。

## 2. 已完成的就业数据场景

业务库：`employment_db`

原始表：`student_placement`

字段包括专业 `branch`、实习次数 `internships_count`、就业状态 `placement_status` 与年度薪资包 `salary_package_lpa`。

建议保留的口径知识：

```text
就业率 = placement_status = 'Placed' 的学生数 / 全部学生数。
salary_package_lpa 表示年度薪资包，单位为 LPA，不是月薪；平均薪资默认只统计 Placed 学生。
```

已验证的典型问题：

```text
各专业的就业率排名如何？
已就业学生的平均年薪是多少？
实习次数对就业率有什么影响？
哪个专业的平均薪资最高？
有挂科记录的学生就业率是多少？
```

## 3. 关联数据分析的正确使用方式

如果新增 `companies`、`job_offers`、`internships` 等表，应明确标注数据来源：

- 原始 Kaggle 文件只提供学生就业预测的单表数据；
- 自行生成的企业、Offer、实习记录只能用于测试多表关联；
- 不能把生成记录的行业/城市/企业薪资结论当成真实就业市场结论。

接入真实数据时，优先使用经过授权、脱敏的数据。不要导入姓名、手机号、学号、身份证号、邮件地址、简历全文等个人信息。

## 4. 新建一个可靠智能体的标准流程

1. 新建并发布智能体，写清它分析的业务范围。
2. 配置聊天模型与嵌入模型，并确认二者启用。
3. 新增业务数据源，测试连接成功。
4. 将数据源绑定到正确的 `agentId`。
5. 更新数据表，勾选最少必要表。
6. 点击“初始化数据源”。
7. 添加业务术语或 FAQ，明确指标口径。
8. 先问一个简单、可手工验证的问题。
9. 再测试多表关联、空结果、边界值和异常输入。

## 5. 推荐测试维度

| 维度 | 示例 |
| --- | --- |
| 计数 | “各专业学生数量是多少？” |
| 聚合 | “已就业学生平均年薪是多少？” |
| 排名 | “就业率最高的专业是什么？” |
| 筛选 | “挂科次数大于 0 的学生就业率是多少？” |
| 分组 | “按学院层次统计就业率。” |
| 关联 | “各行业已接受 Offer 的平均年薪排名。” |
| 空结果 | “查询不存在的专业。” |
| 口径 | “就业率如何定义？” |

## 6. 看到错误时的最短路径

| 页面/日志现象 | 优先检查 |
| --- | --- |
| `No active EMBEDDING model configured` | 嵌入模型是否已启用。 |
| “未找到证据” | 不一定是错误；可添加 FAQ 或业务术语改善效果。 |
| “初步表信息召回数量: 0” | 当前智能体的数据源绑定、选表、初始化、嵌入模型是否变更。 |
| SQL 结果为空 | 先在 MySQL 手动运行同一条 SQL，确认业务表确实有对应数据。 |
| SQL 执行报错 | 检查字段、表名、数据库权限和数据源连接。 |
| 前端连接不到后端 | 确认后端 8065、前端 3000 都在运行，且 `nuxt.config.ts` 的代理未被改坏。 |

## 7. 下一阶段可以做什么

1. 为就业智能体接入可信、脱敏的真实数据，而不是只增加模拟表。
2. 使用“语义模型配置”维护复杂指标、表关系和业务描述。
3. 给常见问题建立回归测试清单：同一句问题每次改动后都重新测试。
4. 阅读 `03-从提问到报告的调用链.md`，在 IDEA 中沿工作流逐步打断点。
5. 为真实业务数据库创建最小权限、只读的专用 MySQL 用户。
